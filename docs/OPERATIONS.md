# 운영 절차

## 모집·명단·출석·이수

1. 최신 승인 대상·기수·시간표·장소·정원·문의 채널을 확인한다.
2. 신청 시트와 재단 LMS 수강신청을 대조한다. 양쪽 신청은 별개다. 기수 불일치·취소·중복·현장 추가를 정리한다.
3. 명단은 인쇄 직전 다시 산출한다. 기존 경로는 `print/build_roster.py`였다. 전화번호 기반 중복 제거 후에도 동명이인은 소속 등으로 구분한다.
4. 현장 출석은 재단 서식을 사용한다. 신청·식수·계정 수로 출석을 대신하지 않는다. 양일 서명과 예외 증빙을 보관한다.
5. 최종 이수는 승인된 기준으로 판정한다. 완료 산출물은 이수 대조표·검토 기록·LMS 반영 증빙이다.

## 문자·공지·문의

입력: 최신 대상자 명단, 기신청·취소·기발송 내역, 승인된 문안.

- 발송 직전 시트·LMS·폼을 재조회한다. 문안의 기수·시간·장소·링크·문의처를 확인한다.
- 뿌리오는 기존 기록상 등록 IP가 필요했다. 과거 `code 1000` 성공 로그로 중복을 막았다. 접수 성공을 실제 수신 완료로 표현하지 않는다.
- 발송결과 조회 API가 없다는 것은 당시 구현 기록이다. 후임 환경에서 현행 기능을 확인한다. 실패·불명확 응답은 무조건 재발송하지 말고 접수 여부부터 조사한다.
- 기배포 Discord 초대는 삭제·재발급하지 않는다. 채널 역할 권한을 조정하고 기존 초대의 접근을 확인한다.
- 완료 기록: 승인 문안 버전, 대상 산출 시각·건수, 실행 담당, 성공/실패/불명확 건수, 비공개 로그 위치. Git에는 개별 수신자 기록을 넣지 않는다.
- CS는 질문·담당·처리상태·회신 근거를 비공개 큐에 남긴다. 개인정보를 제거한 반복 질문만 FAQ로 추출한다.

## 행사·현장 준비

장소 계약·이용시간 → 시간표 → 강사/보조/접수/기술지원 역할 → 계정/네트워크/전원 → 물품/출석/안내 → 비상 대응 순서로 확정한다. 기수별 실제 강사배치표를 읽는다. 자동 생성한 문서보다 사람의 최신 편집을 우선 확인한다.

인쇄물은 재사용 가능한 공통 표지와 기수별 출석부·식권을 분리한다. 출석부는 재단 양식, 식권은 사용일·식당·위치·예외를 검증한다. 규격·부수·납기·배송지·견적·검수 기록을 남긴다.

## 예선·본선

팀별 문제·사용자·결과물 링크·질문을 먼저 수합한다. 플랫폼 목적·계정 지속성·비용·제출과 공개 범위를 명확히 안내한다. 개발자에게는 팀 수와 상담 회차를 기준으로 필요한 인력을 요청한다.

8/20 회의결과에서 확인되는 합의는 팀별 노트북 부스·상호 피드백·발표 도입이다. 개발자 상담소와 수정 스프린트의 상세 흐름은 후속 기획안의 제안이며 별도 승인 확인이 필요하다. 세부 인원·시수·평가기준·시상·최종 제출 형식은 승인본으로 채운다. 교안이나 기획안만 보고 실행·성과를 보고하지 않는다.

## 성과·보고·정산

- 목표·실적·분모·산식·관측일·원자료를 한 표로 관리한다. 사전 수준 문항을 만족도 평균에 무심코 합산하지 않는다.
- 역량 향상률은 사전/사후 문항과 척도·동일 대상 여부를 확인한다. 목표에 맞추려고 사후에 산식을 바꾸지 않는다.
- 보고서는 기수별 실제 운영과 개정 내용을 구분한다. 9/11 원고는 팀모노 담당 구간이며 전체 프로그램 성과 증빙이 아니다.
- 집행 전 승인 예산·비목·실제 비용 부담 주체를 정산 담당과 확인한다. 식대 한도·컨소시엄 분담에는 상충 기록이 있어 이 문서가 정산 해석을 확정하지 않는다.
- 완료 증빙은 계약/견적·사전 결재·참석/수행 근거·계산서/영수증·지급·검수·제출 접수 기록이다. 최신 재단 양식과 요구 목록으로 보완한다.

## 기존 자동화 이관

소스와 비밀키는 별도로 이관한다. `ppurio.py/send_*.py`(문자), `discord_setup.py`(권한), `create_*_form.py`(폼), `attendance.py`(출석), `codle_accounts.py`(계정), `print/`(인쇄)가 주요 후보다.

이들은 완제품 패키지가 아니다. 기수·명단·출석 판독·ID·로컬 경로가 하드코딩되어 있다. 후임 환경에서 코드 검토 → 필요한 기능만 추출 → 비밀정보 외부 주입 → 읽기 확인 → 외부 변경 없는 대상/문안 미리보기 → 승인된 실행 순서로 옮긴다. 이전 발송 중복 방지 기록도 비공개로 인계해야 한다.

Google 생성 API 오류를 Drive 파일 생성/변환으로 우회한 전례는 당시 계정의 관찰이다. 현재 API의 일반 제한이라고 단정하지 않는다. 공동 편집 시트는 수정 직전 셀을 읽고 필요한 셀만 갱신한다. export/import로 통째 덮어쓰면 캐시의 옛 값이 되살아날 수 있다.

## 출석 분모와 플랫폼 상태 전환

CONTEXT §3-19에는 당시 LMS 총 연수시간을 **1,380분(집합 900 + 본선 480)**으로 확인한 기록이 있다. 집합연수만의 900분/720분 기준을 전체 이수 판정에 적용하지 않는다. 다만 최신 회차 LMS와 평가 기준은 다시 확인해야 하며, 출석만으로 최종 이수를 단정하지 않는다. 같은 절에는 수기 서명을 사용하기로 한 결정과 연수 후 출석부를 제출해야 한다는 안내가 있다. 제출 완료 증빙은 별도 확인한다. QR을 필수로 새로 구축하지 않는다.

9/11 조사에 인용된 짓다 참가자 가이드에 따르면 튜토리얼 프로젝트는 본 해커톤으로 자동 승계되지 않고, 진행 중 선택 공개에서 종료 후 전체 갤러리 공개로 바뀐다. 이는 당시 가이드의 동작 설명이다. 현재 운영 화면에서 상태 전환·저장·공개 범위를 먼저 확인하고 참가자에게 알린다. 가이드에서 확인한 소스 ZIP 다운로드는 ‘내 작품’ 기준이며 운영자의 일괄 다운로드 권한은 미검증이다. 도구와 결과물의 이전·보관을 별도 확인한다.

## 누락되기 쉬운 증빙과 후속 처리

- CONTEXT §3-22의 당시 회계 안내에는 API 선결제 증빙과 **행사 기간 내 사용량 증빙**을 함께 확보하도록 기록되어 있다. 결제 영수증만으로 정산 준비를 끝내지 말고 최신 인정 방식을 정산 담당에게 확인한다.
- 같은 절에는 계좌이체 내부 결재와 주간 집행 마감이 있다. 실제 지출 전에 현재 결재 시스템·마감·집행 주체를 확인한다. 상세 분담·금액은 비공개 부록에서 관리한다.
- 전주기 문서 단계3·7~9에 있는 사진·영상 동의, 이수 결과 통보, 사례집·인증 발급을 과업별로 추적한다. 재단 인증과 별도 디지털 배지를 같은 것으로 약속하지 않는다.
- CONTEXT §3-9에 성과물 사사표기 요구가 기록되어 있다. 실제 제출물의 표기 문구·로고·저작권·공개 동의는 승인 가이드와 대조한다.
- 만족도 분석 §6에는 제한된 척도의 상한 때문에 특정 향상률 목표를 달성할 수 없는 문제가 제기되어 있다. ‘산식을 아직 모름’과 ‘기존 산식으로 목표 달성이 불가능함’을 구분하고, 기준 변경은 재단 협의·승인 근거를 남긴다.
